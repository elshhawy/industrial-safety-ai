## 1. System Boundary & Scope

The backend is responsible for:
1. **Validating** incoming structured AI safety events against this contract.
2. **Persisting** events, violations, and alerts into PostgreSQL inside an atomic database transaction.
3. **Preventing duplicate records** on upstream network retries via database uniqueness on `event_id`.
4. **Exposing stable read APIs** for API consumers, MLOps, and future monitoring dashboards.

### What the Backend Does NOT Do
- The backend does **not** process raw video frames, bounding box coordinates, YOLO tensors, or tracking graphs.
- The backend does **not** decide whether a person entered a danger zone or whether a helmet is missing. **Upstream logic makes safety determinations; the backend validates and records them.**

## 3. Data Specification

### 3.1 Field Definitions

| Field Name | JSON Type | Status | Constraints & Description | Example |
|---|---|---|---|---|
| `event_id` | string | **Required** | Length 1–128. Stable identifier generated by the Edge/AI pipeline. Must be retained on retries. | `"evt_CAM01_20261002_143205_001"` |
| `event_type` | string | **Required** | Enum: `person_detected`, `zone_entry`, `zone_exit`, `ppe_violation`, `danger_zone_violation`. | `"ppe_violation"` |
| `occurred_at` | string | **Required** | ISO 8601 with timezone (e.g. `YYYY-MM-DDTHH:MM:SSZ` or with offset). Normalized to UTC by backend. | `"2026-10-02T14:32:05Z"` |
| `camera_id` | string | **Required** | Length 1–64. Identifier of the camera / sensor capturing the event. | `"CAM-01"` |
| `is_violation` | boolean | **Required** | `true` if this event constitutes a safety violation; `false` otherwise. | `true` |
| `violation_type` | string | **Conditional** | **Required if `is_violation: true`**. Must be `null` if `is_violation: false`. Enum: `missing_helmet`, `missing_vest`, `missing_gloves`, `missing_goggles`, `missing_ppe`, `danger_zone_entry_without_ppe`, `danger_zone_unauthorized`, `safety_rule_violation`. | `"missing_helmet"` |
| `severity` | string | **Conditional** | **Required if `is_violation: true`**. Must be `null` if `is_violation: false`. Enum: `low`, `medium`, `high`, `critical`. | `"high"` |
| `track_id` | string \| null | Optional | Upstream tracker object identifier. | `"TRK-42"` |
| `person_id` | string \| null | Optional | Identified personnel / employee badge ID if available. | `"EMP-102"` |
| `zone_id` | string \| null | Optional | Identifier of danger zone or operational area. | `"ZONE-CRANE-A"` |
| `confidence` | number \| null | Optional | AI detection confidence between `0.0` and `1.0` inclusive. | `0.93` |
| `description` | string \| null | Optional | Human-readable explanation of the event or violation. | `"Worker entered zone without helmet"` |
| `ppe` | object \| null | Optional | Structured PPE compliance map (e.g. `{"helmet": false, "vest": true}`). | `{"helmet": false, "vest": true}` |
| `frame_reference` | string \| null | Optional | URI / storage path to the evidentiary image snapshot. | `"frames/CAM-01/evt_001.jpg"` |
| `metadata` | object \| null | Optional | Arbitrary key-value metadata for AI/ML pipeline debugging. | `{"model_ver": "v1.2"}` |

## 4. Contract Rules & Validation

1. **Strict Payload Integrity**: Unknown top-level fields are strictly rejected with HTTP `422 Unprocessable Entity`.
2. **Cross-Field Consistency**:
   - `event_type` `ppe_violation` or `danger_zone_violation` requires `is_violation: true`; all other event types require `false`.
   - If `is_violation: true` → both `violation_type` and `severity` **must** be provided.
   - If `is_violation: false` → `violation_type` and `severity` **must** be `null`.
3. **Idempotency & Retries**:
   - The backend enforces a `UNIQUE` constraint on `event_id`.
   - If the pipeline retries an event with the same `event_id`, the backend rejects duplicate insertion with HTTP `409 Conflict` without modifying existing records or generating duplicate alerts.
   - The sender may treat `409` as delivered only when it is retrying the same event with the same payload. Reusing an ID for a different event is a sender error.

## 5. API Response Contracts

### 5.1 Success Response (`201 Created`)

Returned when the event is accepted, validated, and persisted.

```json
{
  "status": "accepted",
  "event_id": "evt_CAM01_20261002_143205_001",
  "backend_id": "89cc8d12-2d98-4e67-bc43-7b18bcce84af",
  "violation_created": true,
  "alert_created": true
}
```

### 5.2 Duplicate Retry Response (`409 Conflict`)

Returned when an `event_id` that was already accepted is sent again. Upstream can acknowledge delivery when retrying the same event and payload.

```json
{
  "detail": "event_id already received"
}
```

### 5.3 Validation Error Response (`422 Unprocessable Entity`)

Returned when the payload is malformed or violates contract constraints.

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body"],
      "msg": "Value error, violation_type is required when is_violation is true"
    }
  ]
}
```

### 5.4 Internal Server Error (`500 Internal Server Error`)

```json
{
  "detail": "Database integrity error"
}
```

## 6. Upstream Implementation Checklist

When integrating the Real-Time Integration pipeline (Ahmed Selim):
- [ ] Configure backend target endpoint: `POST http://<host>:<port>/api/v1/events`
- [ ] Ensure `event_id` is generated once per safety event and preserved across retry attempts.
- [ ] Ensure timestamps include timezone (UTC recommended: `Z`).
- [ ] Include `violation_type` and `severity` whenever `is_violation: true`.
- [ ] Treat HTTP `201` as confirmed acceptance; treat HTTP `409` as confirmed prior acceptance only when retrying the same event and payload.
- [ ] Log HTTP `422` payload for schema validation debugging.
